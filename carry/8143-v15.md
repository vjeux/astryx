## Why

TransferList lets people order the items they picked, such as columns to show. Its grip grabbed every touch at once, so swiping over grips on a phone didn't scroll the panel.

## What led to it

This is part of the UIKit-parity program, which makes Astryx's components behave like their iOS counterparts on touch screens. Moving Lab's reorders onto core's is part of it. TransferList had its own drag code, duplicating core `List`'s reorder (#8139). The selected panel becomes a core `List` with `reorderable`: hold to drag, flick to scroll, pinch to zoom, and keyboard reorder mode. Following Cindy's direction (her commits are here), `reorderable` takes the `createReorderable` object, with `isReorderable(value)` and `onReorder({key, to})`. TransferListSelector takes it too: in staged mode a move edits the draft, and Cancel drops it.

Before: `<TransferList isReorderable />`. After: `<TransferList reorderable={createReorderable({onReorder})} />`.

This changes desktop behavior too: reordering is opt-in through the owner's object, so a TransferList without `reorderable` no longer reorders with a mouse either (the old `isReorderable` defaulted to true). The spec owners decided on Nov 7 2026 (01:40 UTC) that reordering stays opt-in, a consistency ruling under `spec:AST-103` FR2: one `reorderable` prop, no separate boolean, and TransferList loads no reorder code of its own. TransferList's doc page leads its migration guidance with their sentence: "With no `reorderable`, TransferList no longer reorders; pass `reorderable={createReorderable(…)}`." Cindy's commits are here, and she asked that the doc page and this description carry the migration below.

To migrate:

```tsx
// Before: isReorderable turned reordering on, and an option opted out.
<TransferList options={[{value: 'name', label: 'Name', isReorderDisabled: true}, ...rest]} isReorderable value={fields} onChange={setFields} />

// After: reordering is opt-in through the object createReorderable makes.
const reorderable = useMemo(
  () =>
    createReorderable<string>({
      onReorder: ({key, to}) => setFields(fields => moveTo(fields, key, to)),
      isReorderable: value => value !== 'name',
    }),
  [],
);
<TransferList options={[{value: 'name', label: 'Name'}, ...rest]} reorderable={reorderable} value={fields} onChange={setFields} />
```

TransferList's doc page carries the same example, "Migrating from isReorderable to reorderable".

Core's internal entry `@astryxdesign/core/internal/reorder` comes in here with its first user. It adapts the owner's object, so the panel runs the owner's engine with its own moves, and the owner's `start(key)` still finds the panel's list. Like Core's other internal entries, it is undocumented and outside the public API.

## Options and tradeoffs

- **Keep TransferList's own drag and patch its touch handling,** or reuse core's reorder and change the API.
- **An option that can't move:** a disabled grip, or no grip at all.

## Why this choice

Reusing core's reorder means one implementation, and TransferList gets the hold, the keyboard path and the announcements. The cost is the API change; Lab is private, so there's no changeset. An option that can't move shows no grip (`spec:AST-103` FR1). Reordering pauses while a search filters the panel, where a position is ambiguous. Cindy's `internal/reorder.ts` takes string or number keys to match her #8592, named here for her review.

## A disabled TransferList

On main, a disabled TransferList (#10192) keeps each grip as a focusable disabled control with a "‹label› cannot be reordered" tooltip. This change keeps that on core List's handle. The governing records are `spec:AST-085` FR1 (a disabled control stays in the tab order) and FR4 (focus moves only where the component's record says), with #10192 for the rest. The port's earlier head hid the handles and moved focus to the row's Remove button. This head replaces that.

- Every option is transfer-disabled without its own message, and the search field is disabled but focusable.
- Each selected row is a disabled `ListItem`. Its handle has `aria-disabled`, stays in the tab order and keeps the focus. Keys and drags do nothing: core List ends a reorder mode or sends a drag home when its row becomes disabled.
- Each handle shows main's tooltip on hover and keyboard focus. Its description reads the tooltip text after the list's reorder instructions. TransferList attaches core's `Tooltip` to the handle: the row's last toggle button, which stays core's handle when `renderOption` adds a toggle of its own.
- **Visual change:** a disabled row draws its label and handle at half opacity, core's disabled row. On main the labels keep full opacity. Remove keeps main's half opacity: TransferList drops its own disabled dim inside the dimmed row.

It also ends a text selection on iOS: on main, a finger held on TransferList's grip brings up the loupe and the drag grows a blue selection across the rows (2 of 3 takes on the iOS 26.2 simulator). Core's handle locks selection under a held finger, so this head selects nothing.

## How to check it

In Storybook `Lab/TransferList`:

1. Move a few options to the selected panel.
2. On a phone, hold a grip, then drag. The row moves, and a flick scrolls the panel.
3. Tab to a grip, press Enter, then use the arrow keys; Escape ends the mode.
4. **Locked:** locked options have no grip, and nothing drops above a locked first row.
